## The most important correction to the brief
The brief describes LookLearnFind as a Next.js and Supabase application. **It is not.** There are two separate systems:

| | LookLearnFind (LLF) | The Issues Party (TIP) |
|---|---|---|
| Site | looklearnfind.com | theissuesparty.org |
| Stack | Static site generated by stdlib Python (`build.py`, `elections.py`, `sidebar.py`); a small PHP 8 plus SQLite API for the Look Ledger | Next.js 16.2.7, React 19, Supabase (Postgres), served from the same hosting.com account |
| Content store | HTML files with front matter in `content/`, JSON in `data/`, state files in `data/elections/<ST>/` | Supabase tables (59 relations; 574 races, 6,243 candidates, 1,419 race entries) |
| Database | None for editorial or election content. SQLite holds only Ledger accounts and saves | Postgres, read through the Supabase REST API |
| Candidate pages | **None.** Every LLF candidate row links out to TIP | `/candidates/{fec_candidate_id}` (6,224 in the sitemap) |
| Race pages | State, governor, Senate, House and district pages, generated at build time | `/races/{slug}` (513 in the sitemap), rendered on request |

Anything the planning process assumes about "the database", "Next.js routes" or "migrations" applies to TIP, not LLF. LLF has no database of articles, races, candidates or results to extend. LLF pages are files produced by a build and uploaded as a zip.

## What exists today (Verified)
- **Live LLF site:** 250 built HTML pages, 231 in the sitemap, `robots.txt` open to search engines and closed to AI-training crawlers.
- **Seven state hubs** (Florida, Illinois, Michigan, New York, New Jersey, Minnesota, Pennsylvania) with 6 governor pages, 5 Senate pages, 7 House indexes and **121 congressional district pages**.
- **21 published political articles** (6 State of the Race, 6 Spending Report, 8 Reported Feature, 1 Delta Report; one Reported Feature is spelled with a lowercase "feature" in its metadata) tied to a state, and 6 older sample files that are marked illustrative. There is **no draft or status field**: a file in `content/` is published. Drafts live in `productions/2026/<ST>/`.
- **A candidate directory** at `/find/candidates/` listing 391 registry candidates across the seven states (386 are in the search index; 5 have no TIP profile), each linking to TIP.
- **A sidebar discovery system** with a state lens, driven by `data/discovery.json` (21 story entries, 7 hubs, 3 thread names).
- **A Look Ledger** (PHP plus SQLite): signup, saves, follows, collections and a review desk are implemented. The public list endpoint returned **0 entries** on 2026-11-04.
- **A market and poll monitor** (Kalshi, Polymarket, VoteHub) that last completed a run on 2026-11-03 at 15:26 UTC for 24 monitored races.
- **A per-state production ledger** (`productions/2026/<ST>/STATE_LEDGER.json`) with ChatGPT and Claude handoff packages, an independent fact-check gate and a recorded decision log.

## What does not exist (Verified)
- **No election results.** Neither system stores vote counts, percentages, reporting completeness, race calls or certification status. TIP's `races` table has `result_status`, `result_as_of` and `result_source_url` columns, but all 574 rows hold `result_status = 'none'` and no TIP page reads them. LLF has no results fields at all. The only results-like content is three Florida August primary winners' vote shares stored in `data/elections/FL/story_data.json` and drawn as a bar chart.
- **No county-level voting data.** Congressional district geometry exists for the seven states (Census cartographic boundary file). Only Florida carries county data at all: each Florida district lists its largest counties by share of district area plus a population figure (`counties=True`, used on the Florida House pages). The other six states have `counties=False` and empty county lists. No state has county vote totals.
- **No historical results.** Nothing from 2022 or 2024 is stored.
- **No landing page above the state hubs.** `https://looklearnfind.com/elections/` and `/elections/2026/` return **HTTP 403** because the folders have no index file and directory listing is off. Those two parent URLs are what a "Living State Hub" index would naturally occupy.
- **No CMS or article admin.** The `/admin/` area serves the Ledger review desk only. Articles are edited as files and shipped by a manual zip upload.
- **No automatic rebuild.** Nothing rebuilds or republishes LLF when data changes. The daily monitor writes JSON and copies one status file to the server.

## Constraints that shape any plan
1. **LLF is static and build-driven.** A "living" page means either (a) rebuilding and re-uploading on a schedule, (b) fetching JSON at view time with client JavaScript, or (c) adding server code. Option (b) already exists in two places (`/data/discovery/*.json` and the PHP API).
2. **Results ingestion has no home yet.** It needs a new data layer in whichever system owns it. TIP already has the vocabulary (`races.result_*`, `race_entries`, `candidates`) but no ingestion jobs; LLF has the rendering but no results data.
3. **Provenance rules are strict.** `CLAUDE.md` and `docs/election-build/PUBLISHING_RULES.md` forbid win probabilities, causal claims about spending or prices, rankings and endorsements; reported numbers must be attributed; an unreadable source must be logged in `docs/production/DATA_ACCESS_LIMITATIONS.md`; nothing publishes without owner authorization. A results section will need its own rules, for example for projections and calls.
4. **Only seven of 50 states are built on LLF.** The TIP database holds seed rows for 56 jurisdictions, but LLF hub pages, rosters, markets and articles exist for seven.
5. **Rosters are partly unofficial.** Illinois, New York, Minnesota and Pennsylvania rosters come from Green Papers because the state lists were blocked or not found. Michigan, New Jersey and Florida use official lists.
6. **Staleness.** Florida's market capture is from 2026-10-23, Illinois 2026-10-28, Michigan 2026-10-28. These pages describe pre-primary or pre-election conditions and carry no post-election state.

## Largest regression risks (Verified or Inferred, detail in file 08)
- `build.py --strict` fails the build if a politics story lacks a `data/discovery.json` entry, so adding or changing content has a hard dependency on that registry.
- The 21 article URLs and 121 district URLs are indexed, linked from the sidebar and referenced in handoff ledgers; any renamed route needs a redirect, and **the site has no redirect file** (only three rewrite rules, all for the Ledger).
- `.htaccess` is the only routing layer. Adding new URL shapes (for example `/elections/2026/{state}/results/`) is safe as new files; changing existing ones needs explicit rewrite rules.
- Four state candidate pages are `noindex` today (IL, MN, NY, PA), which is deliberate and should not be undone by accident.

## One-paragraph verdict
The strongest assets for a post-election platform are the per-state hub generator, the 121 district pages, the candidate registry linking to TIP, the discovery sidebar, the Kalshi and poll monitor, the fact-check and handoff workflow, and TIP's `races`, `race_entries`, `candidates` and grade tables. The largest gaps are election results data, a results-capable page type, a place to hold an evolving editorial "ledger" per state, county and historical data, and a publishing path that does not rely on a manual zip. See file 09.
